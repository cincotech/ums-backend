## Analyse du bug : SQLite OK, MySQL silencieusement KO

### La cause racine : `get_or_create` avec des champs non-uniques sur MySQL

Regarde `setup_email_2fa` dans `services.py` :

```python

    user=user,
```

**Le problème :** `get_or_create` utilise **tous les champs passés** comme critères de lookup. Si un `EmailDevice` existe déjà pour cet user mais avec un `name` ou `email` légèrement différent (ex: migration depuis SQLite vers MySQL avec des données existantes, ou une race condition), MySQL va **créer un second device** au lieu de retourner l'existant.

```python

```

### Pourquoi ça marche sur SQLite mais pas MySQL ?

- **SQLite** : pas de contraintes strictes sur les types, les comparaisons de strings sont case-insensitive par défaut, et les transactions sont plus permissives.
- **MySQL** : strict mode activé par défaut, les contraintes d'unicité et les collations sont différentes. Surtout, **MySQL en mode strict peut silencieusement rollback** une transaction si `get_or_create` crée un doublon via une race condition, et retourne quand même un 200 si l'exception est avalée.

### Deuxième cause : `get_or_create` dans `setup_totp_2fa` et `setup_static_2fa`

Même pattern — si un device existe déjà avec un nom différent, MySQL crée un doublon, et le `.get()` suivant explose silencieusement.

```python
if "email_verified" in security_updates:
```

Il manque `instance.save()` après ce bloc si `requires_2fa` n'est pas dans les updates — le `instance.save()` final est conditionnel et peut ne pas être atteint dans certains chemins.

La cause est maintenant parfaitement claire.

## Explication du bug

La migration `0003` qui ajoute `created_by` et `modified_by` **a été créée et appliquée sur SQLite** en local. Mais sur le serveur MySQL, **cette migration n'a jamais été exécutée** — la table `inscriptions` sur MySQL ne contient donc pas les colonnes `created_by_id` et `modified_by_id`.

Quand Django essaie de faire un `INSERT` ou `SELECT` avec ces colonnes → MySQL répond `Unknown column 'inscriptions.created_by_id'`.

**Pourquoi SQLite ne plante pas ?** SQLite est plus permissif sur les types et les colonnes manquantes dans certains contextes, et surtout ta base SQLite locale a déjà la migration appliquée.
